# Catalog Module — Category (CAT-001)

This module currently implements **only Category** (CAT-001 in
`Planning/MASTER_TASK_LIST.xlsx`). Brand (CAT-002), Product (CAT-003), and
ProductVariant (CAT-004) are separate, later tasks — this file documents
Category only and will be extended by those tasks, not rewritten by them.

## Layering

```
Service → Repository → Mongoose Model
```

**No Controller/Route layer exists yet.** `SEC-001`/`SEC-002` (authentication,
organizations, RBAC) haven't been implemented, so there is no authenticated
request context to enforce tenant/permission checks at an HTTP boundary. Adding
routes now would mean either an unauthenticated catalog API or an invented
placeholder auth system — both are explicitly against this project's security
rules. The service layer below is already fully tenant-safe on its own
(every function requires `organizationId`), so once SEC-002 lands, a route
layer is a thin wrapper: read `organizationId` off the authenticated session
and call these functions directly.

## Organization ownership

Category is **organization-owned**, not global/shared. Every category
requires `organizationId`, and every repository function takes it as a
required parameter — not an optional filter that could be forgotten. This is
deliberately the safer default while there's a single organization; a
shared/global category registry is a marketplace concern (MKT-002) to
revisit later, and starting org-scoped doesn't foreclose that.

## Hierarchy

Categories reference their parent via `parentId` (a plain self-reference) —
not a materialized path or nested sets, which would be real complexity this
project's realistic category depth (2–4 levels) doesn't need. `parentId`
absent (or explicitly `null`) means a root category.

Queries:

- Children of X: `findChildren(organizationId, parentId)` — a single indexed
  query. `findChildren(organizationId, null)` matches both categories with
  `parentId` explicitly `null` and categories where the field is entirely
  absent (standard MongoDB null-equality semantics) — verified by a
  dedicated test rather than assumed.
- Deep ancestor/descendant chains (e.g. breadcrumbs) aren't needed yet; if
  they are later, MongoDB's `$graphLookup` aggregation stage can answer them
  without any schema change — no need to introduce it until proven necessary.

**Cycle prevention** (relevant only on update — a brand-new category can't
yet be its own ancestor): before changing `parentId`, the service walks the
_current_ parent chain of the candidate parent; if the category being
updated appears anywhere in that chain, the change is rejected. This also
covers the direct self-parent case. The walk is a simple bounded loop of
organization-scoped lookups — not `$graphLookup` — appropriate for the
shallow trees this catalog will realistically have.

**Cross-organization parent references are rejected**: the service always
re-fetches the candidate parent scoped to `organizationId` before trusting
it — a syntactically valid ObjectId is never treated as proof of ownership.

**An archived category cannot be assigned as a new parent** — prevents
building an active hierarchy under a dead branch.

## Slugs

Generated by a hand-rolled utility (`lib/slugify.ts` — NFKD-normalize, strip
diacritics, lowercase, hyphenate, trim) rather than a dependency; simple
enough not to need one. Unique per `{organizationId, slug}`. On auto-generate,
a collision is resolved by appending `-2`, `-3`, ... — but an _explicitly_
supplied duplicate slug is rejected outright, never silently changed.
Renaming a category does not regenerate its slug — the two are independent
after creation.

**Race safety**: slug uniqueness is enforced by the database's unique index,
not only an application-level existence check. `category.repository.ts`
catches a raw MongoDB duplicate-key error (code `11000`) on both `create`
and `update` and turns it into the same typed `ValidationError` the
pre-check would have produced. For auto-generated slugs, the service retries
with the next numeric suffix specifically when this conflict error occurs,
so a true concurrent-create race still resolves correctly rather than just
failing.

## Lifecycle

`DRAFT | ACTIVE | ARCHIVED`. Archiving is **always soft** — `status` is set
to `ARCHIVED`, the document is never deleted. Archived categories remain
directly queryable (by id, by slug, as another category's child) at all
times; only a future default _listing_ view would exclude them. Archiving a
category does **not** cascade to its children — they keep whatever status
they already had. This is a deliberate choice to avoid a surprising side
effect, not an oversight; an explicit cascade operation could be added later
if real usage shows it's needed.

## Indexes

| Index                                   | Unique | Supports                                            |
| --------------------------------------- | ------ | --------------------------------------------------- |
| `{organizationId, slug}`                | yes    | Slug lookup; per-organization slug uniqueness       |
| `{organizationId, parentId, sortOrder}` | no     | Ordered children of a category, and root categories |

No index on `description` or any field without an actual query pattern
needing one.

## Validation

Zod, `.strict()` on every create/update schema — unknown fields are
rejected outright, not silently stripped. Update schemas never accept
`organizationId`, `_id`, `__v`, `createdAt`, or `updatedAt` — these are
either server-derived or immutable. `objectIdSchema` requires a genuine
24-character hex string (not just anything `mongoose.Types.ObjectId.isValid`
would accept — that check alone also passes any 12-character string, which
would be a false positive here). Pagination (`page`, `limit`) is capped at
`limit: 100` and ready for the future list endpoint to use.

## Serialization

The model's `toJSON` transform strips `__v`. Category has no internal-only
field today (unlike, say, a future Product's cost price) — the transform
convention is established here so later modules follow the same pattern
consistently.

## Testing

`mongodb-memory-server`'s `MongoMemoryServer` (standalone) — no transactions
are needed for category CRUD, so a replica set isn't required here.
