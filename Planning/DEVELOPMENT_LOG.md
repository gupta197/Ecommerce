# Development Log

## Purpose
Chronological record of implementation work, reviews, decisions, testing and releases.

## Development Protocol
1. Select one task from `MASTER_TASK_LIST.xlsx`.
2. Read the task, dependencies and acceptance criteria.
3. Inspect existing code before changing anything.
4. Explain the implementation approach.
5. Implement only the approved scope.
6. Run typecheck, lint and relevant unit/integration/security tests.
7. Perform a security and tenant-isolation review.
8. Update `DEVELOPMENT_PROGRESS.xlsx`.
9. Add significant changes to `CHANGE_LOG.xlsx`.
10. Update architecture/decision documentation when required.
11. Commit changes to Git with a meaningful commit message.
12. Mark the task `COMPLETED` only when acceptance criteria and tests pass.

## Status Values
- NOT_STARTED
- READY
- IN_PROGRESS
- BLOCKED
- IN_REVIEW
- TESTING
- COMPLETED
- CANCELLED

- SEC-001 (Authentication foundation) implemented and marked `COMPLETED` (commit `aaffd29`): new `apps/api/src/modules/auth/` module (`User`, `SecuritySession`, `LoginAttempt` models; concrete repositories; `password.service.ts` (`@node-rs/argon2`, Argon2id), `token.service.ts` (`jose`, HS256 access tokens), `auth.service.ts` orchestrator; `auth.route.ts`), plus `middleware/{authenticate.ts,csrf.ts}` and `lib/cookies.ts`. Hybrid architecture (`ADR-013`): short-lived stateless JWT access token (`sub`/`sid`/`jti`/`iat`/`exp`/`iss`/`aud` only — no roles/permissions/`organizationId`) plus a DB-backed opaque rotating refresh token. Refresh rotation is atomic — a single `findOneAndUpdate` compare-and-swap, not read-then-write (`ADR-014`) — with `familyId`-based reuse detection (family-wide revocation on a reused token) and an absolute 90-day session lifetime bounding the 30-day sliding refresh window; a dedicated concurrency test proves exactly one of two simultaneous refresh attempts on the same token succeeds, with no duplicate replacement session ever created. Registration always hashes the password and never authenticates the caller, including for a duplicate email, with an identical generic response either way (no enumeration). Login failures use a progressive, doubling delay after a grace period — never a hard lockout (`ADR-015`) — alongside the existing IP rate limiter. Cookies are HttpOnly/Secure(prod)/SameSite=Lax, with the refresh cookie scoped to `path=/api/v1/auth`; CSRF uses double-submit plus Origin/Referer validation, applied only to `logout`/`refresh`/`sessions/:id/revoke`/`revoke-others`, never to `login`/`register`. `authenticate()` verifies the JWT cryptographically only, with no per-request MongoDB lookup — an intentional, documented tradeoff given the short access-token TTL; immediate revocation enforcement and step-up re-authentication are deferred to future middleware. Two real issues were found and fixed during implementation: `cookie@2.x` renamed its exports from `parse`/`serialize` to `parseCookie`/`stringifyCookie` (caught via a real `tsc` error, verified against the actually-installed nested package rather than an earlier check that had exercised Express's own older hoisted `cookie` dependency); and four pre-existing test files (`env.test.ts`, `connection.test.ts`, `health.route.test.ts`, `ready.route.test.ts`) needed their local test config updated to supply the newly-required `JWT_ACCESS_TOKEN_SECRET` — a direct, unavoidable consequence of that field becoming required, not a scope refactor. 103 new tests (193/193 total passing), all using `mongodb-memory-server` plus `supertest` for route-level integration tests; test discovery verified genuine (24 test files, exact expected count). 3 new dependencies (`jose`, `@node-rs/argon2`, `cookie`), all pre-verified against the approved plan. No `apps/api/src/modules/catalog/` file touched — verified via `git diff` before committing. Recorded as `CHG-006` in `CHANGE_LOG.xlsx`; three new architecture decisions recorded as `ADR-013`–`ADR-015` in `ARCHITECTURE_DECISIONS.md`.

### 2026-09-13
- SEC-002 (Organizations, memberships, roles and permissions) implemented and marked `COMPLETED` (commit `358b2e2`): new `apps/api/src/modules/organizations/` module — `Organization` and `OrganizationMembership` models (`User` gained no `organizationId`; membership is a separate relationship, since a user may belong to zero, one, or multiple organizations), concrete repositories, `authorization/{permissions.ts,policy.ts}`, `organization.service.ts`, `membership.service.ts`, and `organization.route.ts`. Roles are a fixed `OWNER|ADMIN|MEMBER` enum and permissions are a static, code-defined role→permission map — deliberately **no** `Role`/`Permission` MongoDB collections (`ADR-016`). Organization context is resolved from the untrusted URL `:organizationId` and re-verified server-side on **every** request via `resolveOrganizationContext()` (ObjectId validation → organization existence+`ACTIVE` status → caller's `ACTIVE` membership), never cached in the JWT or session — organization-doesn't-exist, organization-is-suspended, and caller-isn't-a-member all produce a byte-identical generic 403, verified by a dedicated test (`ADR-017`). Last-owner protection uses a denormalized, atomically-guarded `Organization.activeOwnerCount` counter (`findOneAndUpdate` with the count in the filter) rather than count-then-act, specifically because a plain multi-document transaction does not prevent the write-skew case where two concurrent operations each target a *different* one of two owners — a dedicated concurrency test proves this exact race is correctly rejected (`ADR-018`). Organization creation and the creator's first `OWNER` membership are one atomic `withTransaction()` unit (reusing DB-001's existing helper), with a rollback test proving no orphan `Organization` survives a forced membership-creation failure. Membership creation is mass-assignment-proof (`POST .../memberships` accepts only `{userId}`; `role`/`status` don't exist as parameters anywhere in the service call chain). The `ACTIVE→REMOVED` membership lifecycle is terminal for this task, enabled by a **partial** (not blanket) unique index on `{organizationId,userId}` scoped to `status:'ACTIVE'`, so a removed user can be re-added as a brand-new membership document. `req.membership` was added via a **new** `apps/api/src/modules/organizations/types/express.d.ts` using TypeScript declaration merging, specifically to avoid editing SEC-001's own `types/express.d.ts`. By explicit instruction, a `SUSPENDED` organization has no reactivation path for any role, including its own `OWNER` — an accepted limitation, not an oversight, since SEC-002 has no platform-admin capability. 71 new tests (264/264 total passing, zero regression across SEC-001/CAT-001/CAT-002/DB-001/FOUND-002), using `mongodb-memory-server`'s `MongoMemoryReplSet` for every transaction-dependent test and a standalone server for pure single-document-atomic tests. No new dependencies. No `apps/api/src/modules/auth/`, `modules/catalog/`, `db/`, or SEC-001 middleware/types file touched — verified via `git diff` before committing. Recorded as `CHG-007` in `CHANGE_LOG.xlsx`; three new architecture decisions recorded as `ADR-016`–`ADR-018` in `ARCHITECTURE_DECISIONS.md`.
- Post-implementation security review of SEC-002 (PASS WITH LOW-RISK FINDINGS) identified two defense-in-depth gaps, neither exploitable given the code as implemented, both hardened in a single follow-up commit (no architecture change, no new scope):  (1) `organization-membership.repository.ts`'s `updateRole()`/`markRemoved()` filtered only by `_id`, relying entirely on the calling service having already verified `organizationId` via `findActiveById()` moments earlier in the same transaction — both now also filter by `organizationId` directly, so the repository functions are self-defending independent of caller discipline; (2) `Organization.activeOwnerCount` had no schema-level floor — added `min: 0` (document-validation only, the atomic guarded increment/decrement logic that makes a negative value unreachable in practice is unchanged). 3 new tests added (wrong-organizationId no-op for both repository functions, and negative-`activeOwnerCount` rejected on create) — 267/267 total passing, zero regression.

### 2026-09-18
- SEC-003 (Audit/security event infrastructure) implemented and marked `COMPLETED` (commit `b10e976`): new `apps/api/src/modules/audit/` module — a single, append-only `AuditEvent` collection (`repositories/audit-event.repository.ts` exports only `create()`; no `SecurityEvent` collection was created), wired into exactly the 13 sensitive actions verified reachable in the existing SEC-001 (`auth.registration.success/failure`, `auth.login.success/failure`, `auth.logout`, `auth.refresh_token_reuse`, `auth.session.revoke`/`revoke_others`) and SEC-002 (`organization.created`, `organization.suspended`, `membership.added/removed/role_changed`) code — not for any business module without a route layer yet. `organization.reactivated` was deliberately **not** instrumented: re-inspecting `resolveOrganizationContext()` confirmed it blocks every request — including the very `PATCH` that would set `status: 'ACTIVE'` — once an organization is `SUSPENDED`, so a genuine reactivation transition cannot currently occur through any endpoint; the only reachable trigger for that code branch is a no-op. For the three `withTransaction()`-wrapped SEC-002 operations, the audit write happens strictly after the transaction resolves, never inside the callback, since MongoDB's transient-error retry could otherwise duplicate a non-idempotent audit write — proven by dedicated commit/rollback tests. `audit.service.ts`'s `record()` is best-effort and non-blocking (never throws; logs a warning via an optional `logger` parameter when supplied), so an audit outage can never become a login or organization-mutation outage. Metadata safety uses three layers: a scalar-only `SafeMetadata` type (no request-body/document spreading is even possible), explicit hand-built metadata at every call site, and a case-insensitive forbidden-key runtime backstop (`password`, `passwordhash`, `token`, `refreshtoken`, `accesstoken`, `secret`, `cookie`). `auth.login.failure` never populates `actorUserId`/`entityId` for any of its four branches, by explicit locked decision, so a failed attempt's targeted account is never misrepresented as a verified actor; `LoginAttempt` (SEC-001) is completely unchanged and continues to serve its own, separate throttling-signal purpose. `auth.service.ts` gained an optional, trailing `logger?: Logger` parameter on 5 functions that previously lacked one (`register`, `login`, `logoutCurrentSession`, `revokeSession`, `revokeOtherSessions`) — confirmed via inspecting the actual call graph to be the smallest safe change, since the optional/trailing design meant zero of the ~40 pre-existing test call sites in `auth.service.test.ts` needed updating; `organization.service.ts`/`membership.service.ts` needed no signature change at all. 35 new tests (302/302 total passing, zero regression across SEC-001/SEC-002/CAT-001/CAT-002/DB-001/FOUND-002). No new dependencies. No `modules/catalog/`, `db/`, `middleware/{authenticate,csrf,rate-limit}.ts`, or `types/express.d.ts` file touched — verified via `git diff` before committing. No read/query API, no `requestId`/`correlationId`, no TTL/retention policy (explicitly deferred), no GeoIP/device-fingerprinting/detection features. Recorded as `CHG-008` in `CHANGE_LOG.xlsx`; one new architecture decision recorded as `ADR-019` in `ARCHITECTURE_DECISIONS.md`.
