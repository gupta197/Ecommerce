# Development Log

## Purpose
Chronological record of implementation work, reviews, decisions, testing and releases.

## Development Protocol
1. Select one task from `MASTER_TASK_LIST.xlsx`.
2. Read the task, dependencies and acceptance criteria.
3. Inspect existing code before changing anything.
4. Explain the implementation approach.
5. Implement only the approved scope.
6. Run typecheck, lint and relevant unit/integration/security tests.
7. Perform a security and tenant-isolation review.
8. Update `DEVELOPMENT_PROGRESS.xlsx`.
9. Add significant changes to `CHANGE_LOG.xlsx`.
10. Update architecture/decision documentation when required.
11. Commit changes to Git with a meaningful commit message.
12. Mark the task `COMPLETED` only when acceptance criteria and tests pass.

## Status Values
- NOT_STARTED
- READY
- IN_PROGRESS
- BLOCKED
- IN_REVIEW
- TESTING
- COMPLETED
- CANCELLED

- SEC-002 (Organizations, memberships, roles and permissions) implemented and marked `COMPLETED` (commit `358b2e2`): new `apps/api/src/modules/organizations/` module — `Organization` and `OrganizationMembership` models (`User` gained no `organizationId`; membership is a separate relationship, since a user may belong to zero, one, or multiple organizations), concrete repositories, `authorization/{permissions.ts,policy.ts}`, `organization.service.ts`, `membership.service.ts`, and `organization.route.ts`. Roles are a fixed `OWNER|ADMIN|MEMBER` enum and permissions are a static, code-defined role→permission map — deliberately **no** `Role`/`Permission` MongoDB collections (`ADR-016`). Organization context is resolved from the untrusted URL `:organizationId` and re-verified server-side on **every** request via `resolveOrganizationContext()` (ObjectId validation → organization existence+`ACTIVE` status → caller's `ACTIVE` membership), never cached in the JWT or session — organization-doesn't-exist, organization-is-suspended, and caller-isn't-a-member all produce a byte-identical generic 403, verified by a dedicated test (`ADR-017`). Last-owner protection uses a denormalized, atomically-guarded `Organization.activeOwnerCount` counter (`findOneAndUpdate` with the count in the filter) rather than count-then-act, specifically because a plain multi-document transaction does not prevent the write-skew case where two concurrent operations each target a *different* one of two owners — a dedicated concurrency test proves this exact race is correctly rejected (`ADR-018`). Organization creation and the creator's first `OWNER` membership are one atomic `withTransaction()` unit (reusing DB-001's existing helper), with a rollback test proving no orphan `Organization` survives a forced membership-creation failure. Membership creation is mass-assignment-proof (`POST .../memberships` accepts only `{userId}`; `role`/`status` don't exist as parameters anywhere in the service call chain). The `ACTIVE→REMOVED` membership lifecycle is terminal for this task, enabled by a **partial** (not blanket) unique index on `{organizationId,userId}` scoped to `status:'ACTIVE'`, so a removed user can be re-added as a brand-new membership document. `req.membership` was added via a **new** `apps/api/src/modules/organizations/types/express.d.ts` using TypeScript declaration merging, specifically to avoid editing SEC-001's own `types/express.d.ts`. By explicit instruction, a `SUSPENDED` organization has no reactivation path for any role, including its own `OWNER` — an accepted limitation, not an oversight, since SEC-002 has no platform-admin capability. 71 new tests (264/264 total passing, zero regression across SEC-001/CAT-001/CAT-002/DB-001/FOUND-002), using `mongodb-memory-server`'s `MongoMemoryReplSet` for every transaction-dependent test and a standalone server for pure single-document-atomic tests. This is also the **first route layer added since SEC-001/SEC-002** — self-service `/api/v1/customers/me...` endpoints, approved because `authenticate()` is already live and a customer managing their own data is inherently an end-user flow, unlike the catalog/inventory foundation tasks; every handler resolves identity exclusively from `req.auth.userId`. **Audit wiring gap, not silently resolved**: the approved `customer.archived`/`customer.restored` audit events could not be implemented without extending `AUDIT_ACTIONS`/`AUDIT_ENTITY_TYPES` in a SEC-003 file, directly conflicting with this task's explicit "do not modify SEC-003" boundary — resolved by not touching SEC-003 and recording the conflict as `DEC-007` in `OPEN_DECISIONS.md` for a follow-up decision, with a dedicated test proving the current zero-audit-event state. No staff/admin customer APIs, no customer ledger, no organization-level customer ownership, no guest checkout, no orders/cart/payment functionality, no ISO-country dependency — all explicitly out of scope per the approved plan. 101 new tests (572/572 total passing, zero regression — CAT-001-004's 166 and INV-001's 78 tests re-run in isolation and confirmed unchanged and passing, and auth+organizations' 173 tests re-verified unaffected by the shared `routes/v1/index.ts` change), including a dedicated concurrency test for simultaneous `setDefaultAddress` calls and a transaction-rollback test. No new dependencies. No CAT-001–004, INV-001, `modules/auth/`, `modules/organizations/`, `modules/audit/`, or `db/` file touched — verified via `git diff` before committing. Recorded as `CHG-012` in `CHANGE_LOG.xlsx`; one new architecture decision recorded as `ADR-023` in `ARCHITECTURE_DECISIONS.md`.
